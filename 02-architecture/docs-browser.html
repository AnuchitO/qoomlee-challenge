Key Design Decisions

DecisionImplementation
Monolith-friendly modularity2 services, not 8. Each owns its domain end-to-end.
Layered architectureHandler → Service → Repository with interface-driven testability.
Lazy booking expiryPENDING bookings expire on read — no background sweeper needed.
Overbooking preventionSELECT FOR UPDATE locks seat rows under concurrent requests.
Duplicate booking guardbookingToken parameter — same token, same result (idempotency).
Session authOpaque Bearer tokens (JWT RS256 upgrade planned).
Service-to-service authX-Internal-Token with constant-time comparison.
Payment idempotencyOne charge per bookingRef — duplicate attempts return existing receipt.

Architecture

C4 model diagrams showing the system at three levels of detail. Click the tabs to switch views.

Service Details

qoomlee-service (Go + Gin, :9988)

ComponentResponsibility
FlightHandler → FlightService → FlightRepoFlight search (public), flight detail by ID
BookingHandler → BookingService → BookingRepoCreate booking (seat decrement, PNR), get by ref, list all, update status
Middleware: SessionAuthExtract Bearer token → userSub in Gin context
Middleware: InternalTokenValidate X-Internal-Token for service-to-service calls
Middleware: SecurityHeadersCORS, Cache-Control, X-Content-Type-Options, X-Frame-Options
Middleware: RequestIDGenerate correlation ID per request

payment-service (Go + Gin, :9984)

ComponentResponsibility
PaymentHandler → PaymentService → PaymentRepoCharge card, get receipt
OmiseClientCreate charge via Omise API
BookingClientGET booking detail + PUT status update on qoomlee-service
Middleware: RateLimitToken bucket — 10 req/s on charge endpoint
Middleware: SessionAuthSame pattern as qoomlee-service

Data Flow: Payment Processing

1. payment-service receives POST /api/payments/charge 2. └─ GET /api/bookings/:ref (qoomlee-service) → fetch booking details 3. └─ Validate amount matches booking.totalAmountMinor 4. └─ Create charge via Omise API (synchronous) 5. └─ INSERT into payments table (payment-service DB) 6. └─ PUT /api/bookings/:ref/status (qoomlee-service) → CONFIRMED 7. └─ Return payment receipt to caller

Booking Status Lifecycle

PENDING ──── charge succeeds ──► CONFIRMED PENDING ──── charge fails ─────► PENDING (can retry) PENDING ──── expires (15 min) ─► EXPIRED (lazy, on read)

API Reference

All 7 endpoints across 2 services. Extracted from the running codebase.

qoomlee-service — port 9988

Public (no auth)

GET /health/live Liveness probe public
GET /health/ready Readiness probe (DB ping) public
GET /api/flights/search Search flights by origin, destination, date, passengers public

Authenticated (Bearer token)

GET /api/flights/:id Get flight detail by ID session
POST /api/bookings Create booking (optional ?bookingToken= for dedup) session
GET /api/bookings List all bookings session
GET /api/bookings/:bookingRef Get booking detail (lazy expiry on read) session

Internal (X-Internal-Token)

PUT /api/bookings/:bookingRef/status Update booking status → CONFIRMED (called by payment-service) internal

payment-service — port 9984

Authenticated (Bearer token)

POST /api/payments/charge Charge a card via Omise (rate-limited: 10 req/s) session
GET /api/payments/:bookingRef Get payment receipt for a booking session

Auth Details

MechanismHow it works
Session tokenOpaque Bearer token from Authorization header. Set as userSub in Gin context. No JWT verification (yet).
Internal tokenShared secret in X-Internal-Token header. Compared with crypto/subtle.ConstantTimeCompare to prevent timing attacks.
Public routes/api/flights/search and health endpoints — no auth required.
