<div class="qse-eyebrow">DAY 2 · TEST</div>

# Test: automation + exploration

::left::

<span class="qse-pill-sdet">SDET Track</span>

<div class="qse-card mt-2 text-sm">
<b>E2E test</b> = walks a full user journey, start to finish. <b>Playwright</b> = the tool that drives a browser for you — already set up in the repo.
<div class="mt-2">Write one for <b>cancel an order</b>:</div>
<div class="mt-1 qse-text-muted">create order → pay → cancel → verify stock released + refund triggered</div>
<div class="mt-2 qse-text-muted">Save the file into the tests folder ("the suite"), then run one command in the terminal — same as clicking ▶ in your test tool, just typed.</div>
</div>

::right::

<span class="qse-pill-qe">QE Track</span>

<div class="qse-card mt-2 text-sm">
Risk-based exploratory testing — where automation doesn't reach:
<ul class="mt-1 ml-4">
<li>Cancel while page is loading (race condition)</li>
<li>Network drops mid-cancel (resilience)</li>
<li>Cancel twice (idempotency UX)</li>
<li>Invalid order reference (error handling)</li>
</ul>
</div>

<div class="text-sm qse-text-muted mt-4">
For each finding: automate it, or keep it manual — and why?
</div>

# Monitor: RCA when a defect escapes

<div class="text-sm qse-text-muted">Scenario: cancel order returns 500 when the payment service is down — nothing stopped the calls to it.</div>

<div class="qse-card mt-3 text-sm">
<div><b>Detected at</b> → Monitor (production)</div>
<div class="mt-1"><b>Should've caught at</b> → Design (no circuit breaker — stops calls to a failing service) / Test (no chaos test — deliberately breaking things to check)</div>
<div class="mt-1"><b>Root cause</b> (RCA = digging into WHY) → no resilience pattern for the payment service dependency</div>
<div class="mt-1"><b>Prevention</b> → add the circuit breaker at Design, the chaos test at Test</div>
</div>

<div class="text-sm qse-text-muted mt-3">
SDET also runs synthetic monitoring (automated checks that run in production) on the cancel endpoint continuously.
</div>
